# A sheet with text fields over the soft keyboard

_Since 2026-11-20 the vaul sheets with fields stay on the keyboard on Android and iPhone Safari: `ShoppingItemEditSheet`, `ShoppingAddSheet` (autofocus via `focus({ preventScroll: true })`, or Safari pans the page by about 330 px) and `CookingTimersSheet` (its height bounds moved onto the sheet; the hook sets `min-height: 0` while the keyboard is open so the 40vh floor can't beat the fitted max-height). Checked in the iOS Simulator (Safari, real keyboard) and the Android emulator. The drawer in `HouseholdSettings` also has a field and still uses vaul's default; not checked on an iPhone._

**Android (Pixel_10 AVD, 360 × 453 CSS px over the keyboard):** the WebView shrinks, so the sheet keeps standing on the keyboard and `max-h-[90dvh]` gives it 408 px. A Save footer pinned under a scrolling form took 88 of them; the Kategorie picker ended at the form's clip edge and looked covered by "Speichern". Save therefore sits in the same scroll area as the fields (`data-sheet-scroll`): with the keyboard up every field shows and Save peeks out below Kategorie; with it down the sheet looks as before.

**iPhone Safari:** the layout viewport does not shrink and Safari scrolls the page to the focused field ([soft-keyboard.md](soft-keyboard.md)). vaul's `repositionInputs` lifts the sheet by the keyboard's height (`bottom: 330px`, height `visualViewport.height - 26`) but ignores that scroll, so the sheet floated 185 px above the keyboard for Name and flew out of the top for Notiz; vaul's `::after` (the sheet's background, drawn below it) filled the gap as an empty cream band. This happened on the pinned-footer code as well (screenshots of 2026-11-20); the first fix (`e3dd05d`, reverted in `b1caa19`) only made it look worse because Save then scrolled out of the shortened sheet. vaul's own counter-measure (`disablePreventScroll={false}`) never runs for a controlled `open`: it waits for `hasBeenOpened`, which only a `Drawer.Trigger` sets.

**The fix:** `useSheetInVisualViewport(ref, open)` with `repositionInputs={false}` on the `Drawer`. On iPhone and iPad it moves a tapped text field 2000 px up for the frame it takes focus, so Safari does not scroll the page (react-aria's and vaul's trick), and scrolls only the sheet's `data-sheet-scroll` area to the field. While the visual viewport is shorter than `innerHeight` it sets the sheet's `bottom` to the part of the window below the visual viewport (0 if Safari scrolled anyway), `max-height` to 90 % of the visual viewport and `--keyboard-bar: 32px`, which the footer adds to its bottom padding so Save scrolls clear of Safari's floating bar. On Android nothing is below the visual viewport, so it sets nothing. Unit tests in `useSheetInVisualViewport.test.ts`; the E2E (`e2e/shopping-list.spec.ts`, 360 × 453 viewport) covers only the Android case, because WebKit in Playwright has no soft keyboard.

**Still open:** Safari's previous/next arrows do not reach a field scrolled out of the sheet's scroll area (same without the hook). A Radix `Select` closes on any window `resize`, so with the keyboard up the first tap on Kategorie only drops the keyboard.
