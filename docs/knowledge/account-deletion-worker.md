# Account deletion worker

_The durable deletion job (SEC-004) and the provider answers it accepts; PostHog's bulk delete became asynchronous in 2026-09_

The `delete-account` edge function (`supabase/functions/delete-account/index.ts` + `_shared/account-deletion.ts`) requests the deletion (RPC `request_account_deletion` erases the user's rows and inserts a job in `private.account_deletion_jobs`) and then advances the job: PostHog person → RevenueCat customer → Auth user, each step recorded; failures reschedule the job (`retry_account_deletion_job`) and the pg_cron drain (every 2 minutes, `private.invoke_account_deletion_worker`) picks it up again. Deploy through the Supabase MCP `deploy_edge_function` (no CLI on the Mac) with the three files under their `functions/...` paths and `verify_jwt: true`; tests are vitest (`npx vitest run supabase/functions/_shared/account-deletion.test.ts`).

**PostHog `persons/bulk_delete/` answers asynchronously since 2026-09** (seen 2026-09-23, the previous deletion on 09-16 was still synchronous): `persons_deleted` stays 0 and the found persons appear in the new `persons_queued_for_deletion`. The worker required deleted == found, so every deletion failed with `posthog_invalid_response` and retried hourly while the user sat on the app's deletion screen; a probe with a non-existent id returns `{persons_found: 0, persons_deleted: 0, persons_queued_for_deletion: 0, events_queued_for_deletion: false, recordings_queued_for_deletion: false, deletion_errors: []}`. Since commit f80999d (deployed as version 13 on 2026-09-24) deleted + queued must equal found. Kerim's own job was unblocked by hand (`next_attempt_at = now()`) and completed on attempt 3 once PostHog had processed the queued person.

**Design note (Kerim, 2026-09-23):** the client-side processing and success screens that survive a relaunch feel over-engineered; the auth user is deleted last, so a stale session stays valid until the job finishes. `account_deletion_jobs.user_id` is `on delete set null` with `subject_user_id` kept separately, and the iOS client already treats a 401 mid-poll as "auth deletion completed", so deleting the Auth user right in the request (leaving PostHog and RevenueCat to the job) is feasible without losing the job. Open decision.
