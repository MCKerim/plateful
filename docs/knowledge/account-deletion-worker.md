# Account deletion worker

_The durable deletion job (SEC-004): Auth user first since 2026-09-24 (version 14), PostHog and RevenueCat in the background; PostHog's bulk delete became asynchronous in 2026-09_

The `delete-account` edge function (`supabase/functions/delete-account/index.ts` + `_shared/account-deletion.ts`) requests the deletion (RPC `request_account_deletion` erases the user's rows and inserts a job in `private.account_deletion_jobs`) and then advances the job: **Auth user → PostHog person → RevenueCat customer** (since 2026-09-24, version 14; before that Auth came last), each step recorded; failures reschedule the job (`retry_account_deletion_job`) and the pg_cron drain (every 2 minutes, `private.invoke_account_deletion_worker`) picks it up again. Deploy through the Supabase MCP `deploy_edge_function` (no CLI on the Mac) with the three files under their `functions/...` paths and `verify_jwt: true`; tests are vitest (`npx vitest run supabase/functions/_shared/account-deletion.test.ts`).

**PostHog `persons/bulk_delete/` answers asynchronously since 2026-09** (seen 2026-09-23, the previous deletion on 09-16 was still synchronous): `persons_deleted` stays 0 and the found persons appear in the new `persons_queued_for_deletion`. The worker required deleted == found, so every deletion failed with `posthog_invalid_response` and retried hourly while the user sat on the app's deletion screen; a probe with a non-existent id returns `{persons_found: 0, persons_deleted: 0, persons_queued_for_deletion: 0, events_queued_for_deletion: false, recordings_queued_for_deletion: false, deletion_errors: []}`. Since commit f80999d (deployed as version 13 on 2026-09-24) deleted + queued must equal found. Kerim's own job was unblocked by hand (`next_attempt_at = now()`) and completed on attempt 3 once PostHog had processed the queued person.

**Auth first (decided and shipped 2026-09-24, PersonalOS `decisions/2026/2026-09-24-plateful-kontoloeschung-auth-zuerst`):** the request deletes the Auth user itself, so the person is signed out and the address is free immediately and no client needs a progress screen or a launch-time check. `account_deletion_jobs.user_id` is `on delete set null` and `subject_user_id` stays until completion, so the job survives; the migration `account_deletion_completes_after_any_step` (iOS repo) makes `record_account_deletion_step` complete the job after whichever step is last. **Web client** (commits 2400ae9, 7e41f7a, c76cefd): preflight RPC → `operation: "request"` → on any 2xx cancel local notifications, `signOut({ scope: "local" })`, toast; it never calls `operation: "status"`, which stays only for installed old clients (they get 401 once the user is gone and treat it as completed). A job whose provider step keeps failing (e.g. `revenuecat_alias_review_required`) is invisible to the user now; check `private.account_deletion_jobs` for `status <> 'completed'` during maintenance.
