# `signed_in` is captured after identify, magic links included

_Why the sign-in event is not captured at the sign-in call site, how a magic-link sign-in is recognised on web and on Android, and what the in-memory mark cannot cover_

- **The PostHog project stamps person properties onto an event at ingestion and never rewrites them.** An event captured while the browser is still anonymous keeps `email = null` forever: it drops out of every person-property filter (the project's internal-user filter included) and shows as an anonymous person. So `signed_in` must fire *after* `posthog.identify()`, which happens in `useUserData.fetchUserData`, long after any sign-in call site.
- **Mechanism (since 2026-09-11, `src/lib/pendingSignIn.ts`):** the call site *marks* the method before the request (`markPendingSignIn("google")` in `SignUp.tsx`, cleared on failure), and `fetchUserData` *spends* it right after a successful `identify()`. Same design as `AuthStore.pendingSignInMethod` in the iOS repo. Google sign-ins before that date were captured at the call site and are anonymous in the way above; PostHog data is immutable. The signed-out branch clears the mark (a sign-out or deletion cancels any owed sign-in, so the next account in the same page can never inherit it), and a failed identify leaves it pending for the retry.
- **Magic links have no call site, and land differently per platform.** Browser: the session sits in the URL fragment (`#access_token=…&type=magiclink`, or `type=signup` for a brand-new address from the same `signInWithOtp`) and the Supabase client consumes it on its own. `pendingSignIn.ts` remembers the fragment's access token at module load and marks `magic_link` only when the auth-state listener (`useAuthBootstrap`) reports a session carrying that token — a stale link that auth-js fails to consume leaves the stored session's token unmatched, so an ordinary restore is never counted as a sign-in. Android: the link opens the app as an App Link and `AppUrlListener` completes the sign-in with `setSession` itself (the WebView URL is `https://localhost/`, the landing sniff never sees it), so it marks explicitly and clears on error. Before 2026-09-11 a magic-link user only ever produced `$identify` and was missing from every signup count.
- **Do not use the `SIGNED_IN` auth event alone for this.** In `@supabase/auth-js` 2.95 `_recoverAndRefresh` emits `SIGNED_IN` when a stored session is recovered on load and on every tab-focus refresh, so it would count reloads as sign-ins.
- **Known limit:** the mark is in-memory. A page reload between the sign-in request and the identify (say, after the profile load failed and the user reloads instead of tapping Retry) loses it and that sign-in goes uncounted. Accepted; iOS has the same property.
- Contract for `method` values and the rest of the event catalog: `docs/analytics.md` in the iOS repo (`~/programming/ios-native/plateful`).
