# `randomId()`, never `crypto.randomUUID()`

**Symptom (2026-09-17, `androidreview@plateful.test`):** `TypeError: crypto.randomUUID is not a function` on `https://localhost/home` ([PostHog](https://eu.posthog.com/project/105665/error_tracking/01a0af7d-8869-7932-ac2a-5e8a2c9de89e)). The device was a real, current one — Samsung SM-S928B (Galaxy S24 Ultra), Android 12, WebView `Chrome/131.0.6778.200` — i.e. an environment that *should* have the API: `randomUUID` shipped in Chrome 92, and `https://localhost` is a secure context twice over (trustworthy scheme and trustworthy host). **The trigger was never explained.** No polyfill in this repo shadows `crypto`, and nothing in the Vite config touches it.

**Why it mattered more than one event suggests:** the throw landed in `useState(mintDraftIds)` in `NoteDialog.tsx` — a `useState` initializer, so React takes the whole dialog down rather than degrading. The other five call sites minted ids for rows about to be written (`recipeImport.api.ts`, `recipeShare.api.ts`, `recipeImage.api.ts`, `WeeklyPlanDialog.tsx`, `useDeleteAccount.ts`), where a throw loses the user's edit. The web build is exposed too: `crypto.randomUUID` is **secure-context only**, so any non-HTTPS origin loses it regardless of browser age.

**Fix (2026-09-18):** `src/utils/randomId.ts` — try `crypto.randomUUID`, fall back to `crypto.getRandomValues` (works in insecure contexts, predates `randomUUID` by a decade) with the RFC 4122 §4.4 version/variant bits set by hand, and fall back again to `Math.random` so the app stays up. All six call sites converted; `grep -rn "crypto.randomUUID" src` should only ever match the helper's own doc comment.

**The rule:** never call `crypto.randomUUID()` directly in this app. Import `randomId` from `@/utils/randomId`. The ids it mints are row keys and client-side draft handles, never secrets or tokens — that is what makes the `Math.random` last resort acceptable. If a future call site needs a *cryptographically strong* value (a token, a nonce), it must not use `randomId`; it should require `crypto.getRandomValues` and fail loudly when it is missing.

**Not diagnosed, deliberately:** rather than version-gate on a WebView quirk no version check would have predicted, the fix removes the dependency. If the same device class starts failing other secure-context-only APIs (`navigator.clipboard`, `SubtleCrypto`), that is the signal the real cause is a non-secure context and worth chasing then.
