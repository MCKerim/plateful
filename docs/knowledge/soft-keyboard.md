# The soft keyboard: how the app sees it, and what covers the focused field

**Symptom (Android emulator, 2026-11-15, 360 px WebView, German):** in the recipe editor a line tapped low on the screen ended under the Abbrechen/Speichern bar once the keyboard was up, so the next tap could hit Abbrechen and lose the edit. In the cookbook search the tab bar and the + button stood on the keyboard and took about a third of the room left for results.

**How the keyboard shows up.** There is no Capacitor Keyboard plugin. The Android WebView shrinks with the keyboard: `innerHeight` and `visualViewport.height` went from 732 to 453 CSS px on the `Pixel_10` AVD, and every `position: fixed` bar moved up onto the keyboard. Phone browsers (Chrome's default `interactive-widget=resizes-visual`) shrink only the visual viewport, and fixed bars stay behind the keyboard. `useKeyboardOpen` (`src/hooks/general/useKeyboardOpen.ts`) covers both: open while a text field has focus and the visual viewport is more than 150 px below the tallest it has been at this width. A width change starts over (turning the phone, pinch zoom); the focus check keeps a desktop window made shorter from counting.

**The WebView's own scroll ignores scroll-padding.** When the keyboard opens, the WebView scrolls the focused field only until it is inside the shrunken screen, which includes the fixed bar. With `scroll-padding-bottom: 74px` on `html` the field still stayed at 400 to 440 px under a bar at 380 px. `scrollIntoView({ block: "nearest" })` and the caret reveal while typing do honor it. So a page with a fixed save bar marks it `data-save-bar`, `index.css` gives `html` the bar's height plus half a rem as `scroll-padding-bottom`, and the page scrolls the focused field again when `useKeyboardOpen` turns true. Only `AddRecipe` does both; the URL import's one field sits mid-screen and the image import has none, so their identical bars are unmarked.

**Who hides what.** The cookbook passes `showFooter={!keyboardOpen}` to `Layout` (tab bar and cooking pill), and `Fab` returns null while the keyboard is open, on every page. The other tab screens with fields (KI-Koch, Settings, Household) keep the tab bar over the keyboard: the chat input is fixed 5rem above the bar, so hiding the bar there means moving the input too.

**Tests.** In desktop Chromium a viewport that shrinks while a field has focus (`page.setViewportSize`) stands in for the keyboard (`e2e/cookbook.spec.ts`, `e2e/recipe-edit.spec.ts`). The WebView's own focus scroll does not exist there, so the editor test exercises only the app's second scroll. The device check is in [android-emulator-agent-check.md](android-emulator-agent-check.md).
